# 大学レコメンドサービスのシミュレータ設計

2026-09-21

## 目的とスコープ

大学レコメンドサービスのUI・推薦ロジックの変更が、受験生の探索行動と志望校選択にどう影響するかを、実トラフィックを使わずに事前検証するためのシミュレータを設計する。

実ユーザーのA/Bテストは、トラフィックの確保と数週間の待ち時間を必要とする。受験生向けサービスはさらに条件が厳しく、利用が受験スケジュールに強く依存するため、施策を試せる時期そのものが限られる。LLMエージェントによる事前シミュレーションは、この制約下で施策候補を絞り込むための手段として位置づける。

### 位置づけ

本番A/Bの代替ではなく、事前スクリーニングとランキングに使う。先行研究でも、効果量が大きい施策ほど予測が当たり、効果がほぼゼロの施策は方向が反転しやすいことが示されている。したがって出力は「採用可否の判定」ではなく「検証すべき施策の優先順位」として扱う。

### 受験生シミュレータとの関係

学習サービス側で設計中の受験生シミュレータ（KTで状態管理し、LLMで振る舞いを生成する構成）と、同一の学習者状態を共有することを前提とする。学力・信念・特性が進路探索の行動を規定するため、別人格として作ると検証の意味が薄れる。本ドキュメントは進路レコメンド側のシミュレーションに絞って記述し、学習行動側は別ドキュメントを参照する。

### スコープ外

- 最終的な出願・受験結果の予測。数か月にわたる意思決定であり、家族や教師の影響も入るため、本シミュレータの正解値にはしない。
- 純粋なレイアウト差の評価（後述のAPI方式で回す場合）。

## なぜ Agent A/B ベースか

Agent A/B（Northeastern大・Penn State・Amazon、CHI EA 2026）は、ペルソナを与えたLLMエージェントをライブのWebサイト上で大量に走らせ、対照群・処置群に割り付けてA/Bテストを模擬するシステムである。Amazon.comでの事例では、フィルターパネルの簡素化を1,000エージェント（各群500）で検証し、処置群の購入が414件、対照群が403件（χ²(1)=5.51, p=0.03）という差を検出し、並行して実施された人間の大規模実験と方向が一致した。

### 構造が一致する点

- 大学レコメンドの主要操作は「検索 → 条件で絞り込み → 詳細を見る → 比較する」であり、EC検索結果ページの操作構造とほぼ同型である。
- 論文自身が、Environment Parsing Module と Action Execution Module のみサイト固有で、LLM Agent を含む他のモジュールは他サイトへ汎用化できると明言している。移植の境界が明確である。
- LLM Agent 部分は交換可能なモジュールとして設計されており、ReAct や UXAgent を差し替えられる。MCP に近い考え方で、こちらの既存スタックに寄せやすい。

### そのまま使えない点

| 論点 | Agent A/B の前提 | 大学レコメンドでの要件 |
| --- | --- | --- |
| ペルソナ | 生成時に一度作られる静的な人物記述 | 学力・信念が時間変化する動的状態 |
| 意図 | 実験者が例示する買い物タスク | 学力と時期から自動生成される志望条件 |
| 割付バランス | 年齢・性別・世帯収入 | 学力帯・志望分野・志望の強さ |
| セッション | 1セッション20アクションで完結 | 数か月にわたる断続的な検討 |
| 正解データ | 並行実施した人間A/Bの結果 | 出願結果は遅すぎるため短期指標で代用 |

この差分のうち、最初の2行が設計上の中心になる。

## システム構成

Agent A/B の4モジュール構成を踏襲し、入力と各モジュールの中身を大学レコメンド向けに差し替える。

### 入力

1. エージェント仕様：エージェント数、学力帯・志望分野の目標分布、参照する学習者コホート
2. A/Bテスト設定：評価対象のデザインまたは推薦ロジック、追跡する行動指標、シミュレーション時点（7月／9月／12月など）
3. 対照群・処置群として動作する2つの環境（後述のプロトタイプの2バリアント）

### 4モジュール

| モジュール | 役割 |
| --- | --- |
| Agent Generation | Learner State Store から学習者を抽出し、各エージェントのペルソナと intention を生成する。Agent A/B のようにゼロから人物像を捏造するのではなく、既存状態の射影として作る |
| Testing Preparation | 対照群・処置群へ割り付け、学力帯・志望分野・志望の強さの分布バランスを検査し、偏っていれば再割付する |
| Autonomous Simulation | 各エージェントが独立したセッションで perceive–decide–act ループを回し、ステップ単位のトレースを記録する |
| Post-Testing Analysis | 群間で指標を集計し、学力帯・志望分野での層別分析を行う。出力はBigQueryへ |

### エージェント–環境の相互作用

閉ループの3コンポーネントも踏襲する。

- **Environment Parsing**：画面またはAPIレスポンスを、大学カード（名称または匿名ID、学部、難易度帯、所在地、費用、特色）と利用可能な行動空間を含むJSONに変換する。Agent A/B が生HTMLもスクリーンショットも使わずJSONを中間表現にしたのと同じ方針を取る。
- **LLM Agent**：構造化された観測＋ペルソナ＋intention＋行動履歴から次の行動を決める。ここは交換可能に保つ。
- **Action Execution**：構造化行動を実環境の操作に変換する。

### 環境アダプタの二系統

プロトタイプをAPIファーストで作るなら、同じインターフェースの下に2つのアダプタを置ける。

| 方式 | 実装 | 向く検証 | 限界 |
| --- | --- | --- | --- |
| API方式 | Recommend API を直接叩く | 推薦ロジックの比較、大量試行、低コスト | 表示順・視覚的目立ちの効果を測れない |
| ブラウザ方式 | Selenium / Playwright で実画面を操作 | UI・レイアウト変更の検証 | 実行コストが高い |

まずAPI方式で回し、UI変更を検証したくなった段階でブラウザ方式を足すのが現実的である。API方式では、レスポンスに提示順やハイライト情報を含めておくと、エージェントが人間と近いものを見ている状態に寄せられる。

## Learner State Store とペルソナ同期

本設計の中心。Agent A/B のペルソナは生成時に固定される人物記述であり、学力のように時間変化する内部状態を持たない。一方、受験生シミュレータは KT で状態を管理し LLM で振る舞いを生成する。この2つを素朴に接続すると、学力が育つ学習エージェントと、学力を持たない進路選択ペルソナが別人格になる。

### 唯一の正としての状態ストア

正規の学習者状態を1つ持ち、そこから2方向にレンダリングする。

```
Learner State Store（唯一の正）
  認知状態   KC別の習熟度、忘却
  信念       自己評価と真値のずれ
  特性       サボりやすさ、リスク選好、志望の強さ
  文脈       学年、時期、通学可能範囲、費用制約、興味分野
      │
      ├─ 射影A → Learning API を叩く学習行動（学習サービス側）
      └─ 射影B → ペルソナ + intention テキスト（本シミュレータ）
```

学習者IDは両者で共通にする。時点 t のスナップショットを取ることで、7月・9月・12月と進路検討を繰り返し、学力の変化が探索行動の変化としてどう現れるかを観察できる。

### intention を手書きしない

Agent A/B では intention が行動軌跡と終了条件を規定する。ここを状態から自動生成することが、同期の実体になる。

- 入力：KC別習熟度から推定した学力帯、直近の模試結果と信念のずれ、志望分野、通学・費用の制約、現在時期
- 出力：「9月模試でE判定だったので、今の学力で届く範囲の情報系を探す」といった探索意図

これにより、学力が伸びたエージェントは自然に上位帯を探索し、信念が実力より低いエージェントは過度に安全な選択をする、という差が生まれる。ペルソナ側のテキストを人手で書き分ける必要はなくなる。

### ペルソナに何を書くか

Amazonの研究（Data-Driven Persona-Conditioned Agents, 2026）では、デモグラ属性だけのペルソナに落とすとサブスク登録予測の精度が0.80から0.30まで劣化し、行動プロファイルの有無が決定的だった。同じ示唆がここにも当てはまる。ペルソナには人物像だけでなく、学習行動の履歴要約（どの単元でつまずいたか、どのくらい継続できているか）を含める。

同研究では、行動履歴が約20件を下回るペルソナではLLMが一般論に流れて精度が落ちることも報告されている。シミュレーション対象にする学習者は、一定の行動量を持つコホートから選ぶ必要がある。

## 行動空間と測定指標

### 行動空間

Agent A/B の Search / Click Product / Click Filter Option / Purchase / Stop に対応させる。

| 行動 | 内容 |
| --- | --- |
| Search | 分野・地域・キーワードで大学を検索する |
| Filter | 難易度帯、学費、所在地、入試方式などで絞り込む |
| ViewDetail | 大学・学部の詳細を開く |
| Compare | 複数校を比較表に入れる |
| Save | お気に入り・志望校リストに追加する |
| RequestInfo | 資料請求・オープンキャンパス予約に進む（コンバージョン相当） |
| Stop | 検討を終了する（離脱） |

Save と RequestInfo が成果指標、Stop が離脱指標になる。

### 測れるもの

- 群間の成果指標：保存率、資料請求率、セッションあたり保存校数
- 効率指標：セッションあたり行動数、詳細閲覧までの手数、絞り込みの使用率
- 探索の広がり：検討校の難易度帯の分散、志望分野外への越境、上位帯・安全圏の比率
- 層別の差：学力帯・志望分野・志望の強さによる反応の違い。Agent A/B でも高齢層と若年層で逆方向の反応が出ており、この種の部分集団差は検出できる見込みがある

### 測れないもの

- 最終的な出願・受験結果。時間スケールが合わない
- 家族・高校教師・友人からの影響。単一エージェントのセッションには入らない
- 長期の心理変化（志望校への愛着形成、模試結果による志望変更の累積）。時点スナップショットを複数回回すことで部分的に近似するにとどまる

### 人間との行動差を前提に置く

Agent A/B の事例では、人間が平均15.96アクションと探索的だったのに対し、エージェントは約6アクションと目的志向だった。にもかかわらず購入率とフィルター利用は近く、意思決定の結果は揃っていた。同じ傾向を想定し、**絶対値ではなく群間差の方向と順位**を評価対象にする。

## 実験設計と校正ループ

### 割付と質問形式

- 割付は学習者単位。学力帯・志望分野・志望の強さの分布バランスを検査し、偏れば再割付する
- ペルソナ数は数百規模から始める。Amazonの研究では935体のプールを500体に間引いても精度がほぼ落ちず、100体でも競争力があったと報告されている
- 画面や推薦結果を評価させる場合、2案を並べて1〜10で評点させる pairwise rating が最も精度が高かった。単独提示では基準が定まらず精度が落ちる

### 校正ループ

```
既存ログ・過去A/Bでシミュレータを校正
 → シミュレータで施策A/Bの効果を予測
 → プロトタイプで実ユーザーA/B
 → 予測効果と実効果を比較（向き・大きさ）
 → 再校正
```

最重要KPIは施策効果の**予測精度**であり、シミュレータ内部の指標そのものではない。学習サービス側と同じループ構造になるため、比較基盤は共通化できる。

### 評価の型

各施策について、実測の相対効果とシミュレーションの相対効果の符号が一致するかを見る。Amazonの研究では、単純な正解率に加えて sign overlap と sign Bhattacharyya という、確信度まで含めた指標が併用されていた。効果がゼロ付近の施策では符号が容易に反転するため、これらの平滑な指標の方が実務的な信頼性判断に使える。

### 統計的検出力の現実

プロトタイプの実ユーザー数では小さな効果は検出できない。最初は効果の大きい介入（推薦あり／なし、比較機能あり／なし）から始め、シミュレータの予測の向きが合うかを確認する。シミュレータ側は逆に大量に回せるため、実A/Bに載せる施策の順位付けに使う。

## このドメイン固有のリスクと対策

### 1. LLMが大学を知りすぎている

最大のリスク。LLMは各大学の難易度・ブランド・世間的評価を事前学習で既に持っている。エージェントが推薦アルゴリズムの出力ではなく自前の先入観で有名大学を選ぶと、推薦ロジックA/Bの差が観測できなくなる。学習ドメインで言われる「知りすぎ問題」が、進路選択ではより強く効く。

対策：

- **匿名条件を対照として必ず走らせる**。大学名を伏せ、属性（難易度帯、学部構成、所在地、費用、特色）のみを提示する条件を用意する
- 匿名条件で推薦ロジックの差が出るか（ロジックの純粋な効果）と、実名条件でそれがどれだけブランドに食われるか（現実での期待効果）を分けて読む
- 実在しないダミー校を混ぜ、選好が属性から説明できるか、名称由来かを検査する

### 2. 推薦エンジンとエージェントの循環

サービス側の学力推定・マッチングロジックと、エージェントの内部状態を同じ実装・同じパラメータで作ると、モデルが自分自身に同意するだけの評価になる。学習サービス側で指摘されていた循環が、レコメンド側でも同形で再発する。

対策：実装を分けるか、少なくとも別データで推定したパラメータを使う。

### 3. LLM特有のバイアス

位置バイアス、追従性、多数派の過剰代表が知られている。ペルソナ条件付けはこれを部分的にしか緩和しない。対策として、提示順をエージェントごとにランダム化し、pairwise 形式で相対効果を取ることで、一様な positivity bias を相殺する。

### 4. 未成年の個人情報

受験生は未成年が多い。実ユーザーのログからペルソナを構成する場合、保護者同意、個人情報の最小化、仮名化を最初から設計に入れる。Amazonの研究でも、ペルソナは匿名化・集計済みの行動シグナルから生成し、推定したデモグラ属性は個人に紐づけず集団シミュレーションの条件付け変数としてのみ扱う、という整理がされている。同じ方針を採る。

### 5. トラフィックの隔離

推薦ポリシーがオンライン学習する場合、シミュレータのデータが混ざると実ユーザーへの推薦がシミュレータの癖に引っ張られる。本番とシミュレーション用で環境を分け、加えてイベントスキーマに `is_simulated` フラグを持たせて二重に防ぐ。

### 6. コスト

Agent A/B の事例では1,000エージェントで推定8.75億トークン、約2,925ドルだった。ブラウザ方式は特に高コストになるため、API方式を主軸に、ペルソナ数の間引きを併用する。

## 検証用プロトタイプ（大学レコメンドサービス）

学習サービスと同様に、シミュレータの予測を実ユーザーで検証する介入実験の場が必要になる。既存ログだけでは現行施策下の行動しか分からず、施策を変えたときの予測精度を検証できないためである。

### 役割

1. 介入実験の場：推薦ロジックやUIを切り替えて実ユーザーA/Bを回し、予測効果と実効果を比較する
2. シミュレータに必要な信号の計測：検討校の比較行動、志望の確信度、除外理由など、既存サービスでは取りにくい信号を取る
3. シミュレータの接続先：人間とシミュレータが同じAPIを使うことで、ログが構造的に一致する

### 機能要件

| # | 機能 | 内容 |
| --- | --- | --- |
| 1 | オンボーディング | 現在の学力（模試結果または診断）、志望分野、通学可能範囲、費用条件、志望の確信度 |
| 2 | 大学データベース | 学部・学科単位のメタデータ、難易度帯、入試方式、費用、所在地、特色タグ |
| 3 | 推薦エンジン | 差し替え可能な複数ポリシー（人気順、条件マッチ、学力適合、興味ベースの協調フィルタ）。これが介入変数になる |
| 4 | 検索・絞り込み | 条件フィルタ。UI変更の検証対象にもなる |
| 5 | 比較機能 | 複数校の並列比較 |
| 6 | 志望校リスト | 保存、チャレンジ・実力相応・安全の帯分け |
| 7 | 資料請求導線 | コンバージョン指標 |
| 8 | 計測 | シミュレータと同一のイベントスキーマ。滞在時間、除外理由タップ、確信度 |
| 9 | 実験基盤 | 学習者単位の割付、フィーチャーフラグ、割付・露出ログ |
| 10 | 運営ダッシュボード | 実験群ごとの指標と、シミュレータ予測との比較 |

### アーキテクチャ

| コンポーネント | 役割 | 実装イメージ |
| --- | --- | --- |
| Web UI | スマホ中心の薄いフロント | Cloud Run |
| Recommend API | 検索、推薦、詳細、保存、イベント受付 | FastAPI on Cloud Run |
| Recommender | ポリシーのプラグイン群 | Recommend API から呼び出し |
| Experiment Service | 割付とフラグ管理 | Firestore |
| University Registry | 大学・学部マスタと属性 | シミュレータと共有 |
| Learner State Store | 学習者状態 | 学習サービスと共有 |
| Event Pipeline | イベント取り込み | Pub/Sub → BigQuery（シミュログと同スキーマ） |
| Simulator Orchestrator | エージェント生成・割付・実行・集計 | LangGraph（Supervisor） |

APIファーストで作り、UIはAPIの薄い皮にする。シミュレータは同じRESTまたはMCP経由で同一APIを叩く。この構造にすると、前掲の Environment Parsing 相当がAPIレスポンスの整形だけで済む。

### 学習サービスとの関係

Learner State Store と Event Pipeline は共通化する。シミュレーション時計、`is_simulated` フラグ、隔離環境といった仕組みも両方で使い回せる。逆に言えば、状態ストアのスキーマは学習・進路の両用途を見てから確定させる必要がある。

## 進め方

1. **Learner State Store のスキーマ確定**：学習行動と進路探索の両用途を見て、認知状態・信念・特性・文脈の4領域を定義する。ここが全体の土台になる
2. **射影Bの実装**：状態からペルソナと intention を生成するモジュールを作り、数体分の出力を人手で読んで妥当性を確認する
3. **API方式のシミュレータMVP**：University Registry と Recommend API のモック、2種類の推薦ポリシー、100体規模のエージェントで perceive–decide–act ループを回す
4. **匿名条件の検証**：実名・匿名の2条件で同じ実験を走らせ、ブランド効果の大きさを測る。ここで匿名条件でも差が出ないなら、シミュレータの感度が不足している
5. **プロトタイプの公開**：実ユーザー向けにサービスを出し、同一APIとイベントスキーマでログを蓄積する
6. **校正ループの起動**：効果の大きい介入から実A/Bを回し、予測の向きが合うかを確認する
7. **ブラウザ方式の追加**：UI・レイアウトの検証が必要になった段階で Environment Parsing と Action Execution を実装する

### 次に決めること

- Learner State Store を学習サービス側と共有するか、進路側は読み取り専用のレプリカにするか
- 大学データの入手経路（公開データ、提携、スクレイピング）とライセンス
- 実ユーザーの集客方法と、未成年の同意取得フロー
